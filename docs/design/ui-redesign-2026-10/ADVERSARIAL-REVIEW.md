## 2. 设置 IA 深度分析(问题 1 的回答)

### 2.1 现状 11 分区逐个盘问

| 现有分区 | 实际内容盘点 | 判定 |
|---|---|---|
| 通用 | 审批模式滑块(概念已上移 composer)+ 语言 + 简单/开发模式 | **内容过薄**,且审批模式与「权限」概念重叠 —— 一个设置出现在两个心智位置 |
| 外观与主题 | 12 主题、字号缩放、密度、终端配色 | 独立成立 |
| 模型 | 服务商/密钥/参数/模型目录 | 独立成立(BYOK 是核心差异,必须一级) |
| 权限与安全 | 权限档、规则、沙箱 | 独立成立,且应接收「默认执行档」 |
| 网络 | 代理、超时、更新检查 | **长尾低频**,撑不起一页 |
| 会话 | 会话默认行为 | **内容过薄**,本质是「通用偏好」 |
| 通知 | OS 通知 + Discord webhook | 独立成立(有真实配置与 R2-P1-7 修复点) |
| 连接 | 引擎/网关/手机配对 | 独立成立(移动审批是差异化) |
| 远程执行 | SSH/Docker 主机 | **与连接心智相同**(都是「agent 在哪跑、连谁」),且凭据约束同源(走系统 ssh) |
| 关于 | 版本/协议/更新 | 独立成立(惯例) |
| 高级(dev) | 开发开关 | 独立成立(dev 门控) |

**结论:部分子页确实多余** —— 不是功能多余,是「分区」多余。11 页里 4 页(通用/网络/会话/远程执行)无法各自撑起一屏实质内容;竞品水位是 6-7 组(Claude Desktop ≈ 7 组平铺、ZCode ≈ 6 组、Codex 更少),Shannon 8 组已在上限。

### 2.2 重组方案(11 → 8)

| 新分区 | 吸收 | 内容要点 |
|---|---|---|
| **通用** | +会话 | 语言、简单/开发模式、启动行为、会话默认(工作目录/草稿/归档)、数据导出 |
| **外观** | —(更名) | 主题 12 选、字号、密度、玻璃强度(新增:材质降级档) |
| **模型** | — | 服务商/密钥/参数(保持) |
| **权限与安全** | +审批默认档 | 默认执行模式四档、工具规则表、出站密钥扫描、注入/签名扫描、沙箱档 |
| **通知** | — | 桌面通知、事件矩阵、Webhook(含「测试用已保存配置」诚实 hint) |
| **连接** | +远程执行+网络 | 引擎/网关、手机配对、SSH/Docker 主机、代理与超时 |
| **关于** | — | 版本、协议、更新 |
| **高级(dev)** | — | 开发开关、功能 flag、诊断 |

**实施备注**:路由层面 `/settings/network|session|remotes` 保留并 301 到新分区锚点,不破坏现有深链;实施时每分区一个 tab,内部用锚点分组。

**已补齐设计稿**:S1 通用 · S2 外观 · (模型=原 12 页) · S3 权限与安全 · S4 通知 · S5 连接 · S6 关于与高级。

### F-4 / F-5 状态矛盾 —— **推荐:直接修(无决策空间)**
- F-4:图表标题跟随筛选动态化;mockup 中 pill 与标题统一为「近 7 天」。
- F-5:阻塞态 agent 负载显示「—」并加 title「阻塞中不消耗算力」;「待人工介入」卡与看板卡统一显示同一阻塞时长。
- 理由:这两处不是方案分歧,是本稿自己违反自己的规则,留着会削弱审查可信度。

### F-6 指挥台导航归属 —— **推荐:A′ 模式感知常驻**(A 的收紧版)
- **选项**:A 全站侧栏常驻 / B 收进任务页子区 / A′ 开发模式全站常驻 + 简单模式隐藏(任务页给入口卡)。
- **证据**:
  - 多智能体为核心卖点的产品,该能力全都是一等表面:WorkBuddy(多 agent 并行是产品主轴,100+ 专家团队一句话并行)、ZCode(左栏一级「并行任务」)、Claude(Cowork 为三大一级 tab 之一)。只有单线程心智的 Codex 没有此类入口。
  - Shannon 现有代码里侧栏本就有简单/开发模式门控(用量/OPC 仅开发模式可见)——A′ 与既有机制完全同构,不引入新模式。
  - B 的问题:指挥台与任务页心智不同(一个是「排期的自动化」、一个是「当下并行的 agent」),塞一起会重演 2026-09 审计批评过的「任务页 7 控件无主次」。
  - 本稿全部 mockup 侧栏脚都标着「开发模式」,所以 **F-6 在稿内的正确形态就是:所有页面的侧栏都应出现「指挥台」**——目前只有 09 有,这本身就是待修的不一致。
- **推荐**:A′。实施:① 全部页面侧栏导航区追加「指挥台」项(现有 19 页机械改动);② 简单模式规则写进 README:导航 6 项对简单模式,开发模式 7 项;③ 任务页顶部预留指挥台入口卡(简单模式用户路径)。
- **风险**:低。代码侧只是 Sidebar 的既有条件渲染加一项。

### F-7 次要文字对比度 —— **推荐:采纳,提亮 t3 + 使用规则双约束**
- `--t3: #6F7488 → #7E839A`(玻璃底上 ≈4.6:1,过 AA);同时立规则:t3 仅用于 ≥12px,10.5-11px 元数据一律用 t2。
- 理由:来源链/时间戳是本稿最高频的小字;且真实仓库的主题生成器本来就拒绝不达 AA 的配对 —— mockup 与管线对齐,避免"设计稿定了实现又被生成器打回"。

### F-8 焦点环 —— **推荐:采纳(CSS 两行)**
- `:focus-visible { outline: 2px solid var(--vio); outline-offset: 2px; border-radius: inherit }`。无争议,仓库现有 axe a11y 基线会直接受益。

### F-9 composer 三要素响应式 —— **推荐:两级降级,阈值 1360 / 1200**
- **方案**:`<1360px` 右停靠自动折叠(留 iconbtn 呼出);`<1200px` 执行模式四档 seg 折叠为「当前档 chip + caret」(点开才展开四档),模型/推理 chip 保持。
- **落选方案**:三要素上移顶栏 —— 刚被你否掉(与 composer 重复);composer 横向滚动 —— 隐藏控件比折叠更伤。
- **证据**:Tauri `minWidth=800`;Codex/Claude 在窄窗都是先收面板、再收控件形态。降级后三要素仍全部可达,只是形态变化,不破坏「composer 恒见三要素」的核心语法。

### F-10 命令面板设置组 —— **推荐:采纳,随新 8 分区更新**
- 面板设置分组列全 8 项(通用/外观/模型/权限与安全/通知/连接/关于/高级),兑现「面板是设置万能入口」(R2-P1-9)。

### F-11 连接卡解剖统一 —— **推荐:采纳**
- Slack 卡补「去认证」主按钮;规则写死:每卡 = 状态徽章 + 一句描述 + 安全徽章 + 底部一个主操作(已连接→管理 / 需认证→去认证 / 未装→添加)。

### F-12 玻璃层预算 —— **推荐:采纳,规则补丁一句话**
- 「弹层打开时,右停靠玻璃降级为实体色」。既守住 ≤4 层红线,实现上也少一次合成;视觉上弹层获得注意力是符合意图的。

### F-15 「任务」一词双载 —— **推荐:保留「任务」,语境消歧;备选「委派」观察后启用**
- **选项**:改「工单」/ 改「委派」/ 保留。
- **分析**:「工单」在中文语境强绑定售后/IT 服务台(Zendesk、运维工单),用在 agent 工作项上会误导;「委派」对应 Claude 的 Dispatch,气质对但作名词略生硬;竞品普遍超载使用 task(Codex 的后台任务/线程、Claude Cowork 的 tasks、Notion),一词多义是行业常态,靠容器消歧。
- **推荐**:保留「任务」,做两个零成本缓解:① 指挥台副标题已写「一个使命,一组 agent,并行推进」,补一句「并行执行中的任务」明确容器;② 若日后用户测试出现混淆,再把看板卡改称「委派」(单点文案改动,随时可切)。不建议现在引入新词。

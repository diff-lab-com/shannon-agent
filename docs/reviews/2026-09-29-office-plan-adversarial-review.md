## 2. 🔴 红色发现（方案级错误/冲突）

### R1. A2「沿用 PDF 注入模式与限额」= 把刚批评过的缺陷复制进新功能

- **问题**：主报告 §9-P1#5 刚把「PDF 50KiB 静默截断」列为缺陷（无页范围、静默丢内容），A2 却写明 docx/xlsx「沿用 PDF 的注入模式与限额」——等于给 docx/xlsx 造一个同款黑洞。一份 20MB 的合同 docx 或 50 万行 xlsx 按 50KiB 注入，用户得到的又是「模型只读了开头」且无提示。
- **修正**：A2 验收标准必须包含——① 按文档结构分节注入（docx 按标题层级、xlsx 按工作表）；② 超限时**显式截断提示**（「已注入前 N 节 / 共 M 节，完整内容可用 read_document 工具分页读取」）；③ 配套一个分页读取工具（复用 Read 工具模式），把「一次性注入」改为「摘要优先 + 按需深读」。

### R2. A3 与 B1 依赖倒置：先装官方技能、后建运行环境，会重演「空壳销售」

- **问题**：A3 建议联邦 anthropics/skills 官方 docx/pptx/xlsx/pdf 四件。但这四件的运行前提是 Claude 式 **code execution 沙箱（预装 python-docx/openpyxl 等库）**——Shannon 没有这个环境（B1 才计划建）。在宿主无对应 Python 库的机器上，装出来的就是又一个「装了不能用」，与 §9-P0#4 刚批评的 stub 销售是同一个错误。另外把上游技能内容**编译期内嵌**（bundled.rs）与**联邦下载**在许可/来源上是两回事，方案未做核验。
- **修正**：A3 v1 只复活**自有 stdlib 三件**（docx-report/xlsx-table/ppt-outline 本就零依赖+诚实降级），按 python3 探测结果条件显示+缺失引导；官方四件移到 B1 交付之后；内嵌前补许可/来源核验清单项。

### R3. B6 的「SMTP 直发」是投递力、滥用面、凭据三重坑

- **问题**：桌面应用直发邮件会撞 SPF/DKIM/DMARC（送达率不可控），发信凭据与 IMAP 收信凭据是两套（多数邮箱要专用授权码），且本地 app 的 SMTP 发信能力是个可被滥用的垃圾邮件面。方案未评估。
- **修正**：B6 v1 改为——① 产出写入 **IMAP Drafts**（用户在熟悉客户端里核对后发送，天然符合「AI 提议、人确认」）；② 投递走 **IM webhook**（Slack/飞书自定义机器人 webhook），复用 improvement-plan 已决议的 5 渠道线；③ SMTP 直发降为 P2 可选项。顺带收益：Drafts 方案让 B6 不再依赖 B3 的 IMAP fetcher 先行（可并行）。

### R4. B7「写操作默认 diff→批准→应用」与现有权限体系冲突，对开发线是倒退式摩擦

- **问题**：Shannon 已有 8 档权限模式+审批弹窗；引擎写操作已有成熟的批准语义。让**所有**写操作变成 diff-first，开发者的批量重构（Edit/MultiEdit）会被 diff 确认淹没——这是拿办公场景的需求惩罚开发场景。
- **修正**：diff-first 只作用于**办公产物路径/非工作目录**（或做成独立权限 profile 供办公用户开启）；Diff viewer 本身（RightDock 渲染 `get_file_diff`）无争议，保留为 Wave 2。

### R5. 与既有 roadmap 的三处冲突/重复（程序问题，最重）

`docs/improvement-plan-2026-09.md`（2026-09-05 评审后含决议记录）与本方案的关系未被引用，产生三处硬冲突：

- **a. 推翻 P2-3 瘦身决议却未声明**。决议原文：「办公线按瘦身方案保留（**P2-3 降为 2-3 个社区级 docx/xlsx skills** 试水，4-6d；不做交付物大屏；若 traction 好，交付物视图下季度再评估）」（`improvement-plan-2026-09.md:39,157,184`）。本方案（B2 三段式 PPT、B3 数据源、B5-B9、C1-C8）规模数倍于该决议。**这不是不能改——本次调研恰好提供了支持扩线的证据——但必须显式写「本方案修订/取代 P2-3 决议，理由如下」，由用户重新裁决，而不是默认 expansion。**
- **b. B5/B6 与 Wave A P0-3 同赛道未拼接**。P0-3 正在做「自动化收件箱：routine 产物进 Triage + 原会话续跑 + API endpoint 触发器 + SQLite」（`improvement-plan-2026-09.md:67-82`）。本方案 B5（办公模板包）、B6（结果路由）是它的**下游扩展**，应写成「P0-3 之上的增量」并复用其收件箱语义与触发器底座，而不是平行再造一套。
- **c. A4 与 P0-1 机制重叠**。P0-1 已建立「README 事实一致性」的机制（单一事实源+生成式 README+CI drift 检查）。本方案的 A4（README 办公宣传对齐）应作为 P0-1 机制下的一个条目（补充功能宣传维度的 drift 检查），而非独立另起。
- **附带重复**：主报告 §9-P2#17（预算上限）与 improvement-plan KPI「会话成本可见性 Wave A 三项全有（含预算）」重复，应从本方案问题清单销账。

### R6. Wave 1「止血，2 周内」的排期失真：A1 把引擎级工程藏进了止血包

- **问题**：A1（转换管线）以 A2（引入 roxml/calamine/csv 三个新依赖 + 解析 + 注入 + 限额 + 测试）为前提，这至少是 1.5-2 周的独立工程，与 A3-A5（UI/文案级）不是一个量级。「2 周止血」承诺会跳票。
- **修正**：拆分——**A1a（天级）**：仅做「明确拒收」：office 类型拖入时 UI 即时提示「暂不支持解析，内容未发送给模型」+ MIME 表补全 + 文档引导。这一条不依赖任何新依赖，本周可上，且已消灭 90% 的信任伤害。**A1b=A2**（转换管线）移入 Wave 1.5 独立排期。

## 3. 🟡 黄色发现（范围/技术风险）

### Y1. B2 全量三段式是一个「mini 布局引擎」，Wave 2 里最可能烂尾的项

OOXML「版式约束模板」（占位符+自动适配防溢出）+ 逐页局部重生成，意味着自研排版引擎的雏形；行业实测（51CTO）也指出模板是约束系统而非皮肤。质量风险不对称：**一套丑 PPT 比没有 PPT 更伤产品**。
**修正**：B2 v1 降维为「大纲确认 UI + 单一极简 OOXML 模板 + 质量门槛（可打开、文本不溢出）」；模板系统与逐页局部重生成挪 Wave 3 与 C5（风格反提，从用户已有 pptx 提取主题，可能比自建 3-5 套模板更便宜且更个性化）合并评估；HTML deck（reveal.js 预览+pptx 经检测到的 LibreOffice/pandoc 导出）作为 stretch。

### Y2. 生成路线未评估「Rust 原生」选项，python3 悬崖可部分拆除

方案默认「生成=Python 技能包」（继承 Claude 路线），但 Shannon 是 Rust 引擎：**xlsx 写入用 rust_xlsxwriter（含公式支持）、docx 用 docx-rs，可引擎原生完成，完全不依赖宿主 python3**；pptx 的 Rust 生态弱、保留技能路线。已核验：当前仓库无任何相关依赖（grep *.toml 零命中），不存在冲突。
**修正**：B1 改为混合策略——xlsx 引擎原生（覆盖最高频办公产物、消灭最大依赖悬崖）、docx/pptx 走技能+python 探测引导、sidecar uv 打包（体积/许可/平台成本）降为 stretch。此决策见 §9-Q1。

### Y3. B3 范围失控风险：IMAP 是大工程，Obsidian 会滑向 RAG

IMAP IDLE+MIME 解析+凭据+正文缓存是一个独立产品的工作量；Obsidian「vault 索引」做深了就是向量 RAG——与 Shannon 已裁决的「无向量、agentic grep」立场（2026-09-05 报告）冲突。
**修正**：B3 v1 收窄并写明边界——IMAP：最近 N 天未读 + 正文 HTML 清洗 + **过 prompt injection 扫描器**（仓库已有 `desktop/src/extensions/security.rs` 等设施）+ 来源标注注入；Obsidian：mtime 增量 + 关键词/近因排序摘录注入；验收明示「非 RAG，深检索走 agentic grep」。

### Y4. B9 复制式文件库违背本地优先

把上传物/生成物复制进 `~/.shannon/files/` 会制造两份真相+双倍磁盘占用；ChatGPT 需要复制是因为云端，本地 app 不需要。
**修正**：B9 v1 = 引用+索引（路径+元数据+缩略图+收藏标记，原文件不动）；「复制入库存档」仅作为显式动作。存储配额逻辑（SaaS 思维）删除，换成 GC/清理策略。

### Y5. C2 批量表格视图撞在未裁决的 Tasks IA 上

2026-06 竞品分析已把「Tasks 页定位模糊」列为 P0 信息架构问题（后台任务/goal/团队混在一起），P0-3 又在往 /triage 里加语义。C2 再加一个重视图会让 IA 更糟。
**修正**：C2 前置条件 = Tasks IA 裁决完成；短期可把「列批量执行」做成 Chat 内 artifact 交互（复用 DocumentRenderer 表格）而非新页面。

### Y6. C3 伴随窗口低估了 Tauri 单窗口架构成本，且与既有工作区决议未对齐

AppContext 是中心化单窗口状态；第二个 webview 意味着状态同步/事件路由/窗口状态持久化的架构改造，不是「加个置顶小窗」。同时 improvement-plan 决议的工作区分期顺序是「**多窗口 → 预览自检 → 面板化 → 集成终端**」——多窗口已排第一，C3 应搭它的车而非独立立项。
**修正**：C3 改为多窗口里程碑的衍生项，spike 后再排期。

### Y7. 安全横切整段缺失

两个新攻击面没有出现在方案任何一条里：① A2 解析**不可信文档**——zip 炸弹、XML billion laughs、超大解压比（docx/pptx 本质是 zip+xml）；② B3/B4' 注入**不可信文本**（邮件正文、转写文件）是最经典的 prompt injection 载体。仓库已有附件校验（`attachments.rs`）与 injection 扫描器（`extensions/security.rs`），方案未引用。
**修正**：A2/B3/B4' 的 DoD 各加一条：解压比/条目数/尺寸护栏 + 注入内容过扫描器 + 引用内容标注来源。

### Y8. 平台矩阵缺失，Windows 是降级链的最大破口

pdftotext（poppler）Windows 无预装；python3 Windows 常缺；A3/B1 的「探测引导」在 Windows 上引导成本最高。方案的降级链没有按平台算过账。
**修正**：补平台矩阵表（macOS/Windows/Linux × python3/poppler/LibreOffice/AppleScript）；A2 顺带评估 Rust PDF 文本提取 crate（pdfium-render/pdf-extract）替代 pdftotext——一次解决 Windows 平价+页范围控制+进程外依赖三件事。

## 4. 🔵 蓝色发现（完整性缺口）

1. **i18n 工作量零出现**：仓库规范要求 en/zh-CN 同一变更内更新 + 8 套机翻过 i18n-check 门禁；A1a/A5/B2/B8/B9 全部触发。且本报告已确认桌面 i18n **没有** sheet/slide/calendar/会议类 key（§9-P2#15），办公线 UI 文案几乎全部新增。
2. **工程门禁零出现**：新增 Tauri 命令必须同步 `desktop/acl/app-permissions.json` + capabilities（ACL 覆盖测试把关）；vitest 覆盖率门禁 80/60/75/80；`VITE_MOCK_MODE` demo 构建需同步 `lib/mock/handlers.ts` 否则演示模式碎掉。A1a/A5/B1/B9/B2 至少各新增 1-2 个命令。
3. **无成功度量**：improvement-plan 有 KPI 表先例，本方案 0 指标。建议至少 3 个：附件处理成功率（office 类型附件→成功注入比例）、办公产物生成成功率（技能执行→文件可用）、routine 办公交付打开率（Triage 条目→被打开/导出比例）。
4. **B3 与 C8 重复**：原 B3 内含「引用锚定 UI」，C8 又列「引用溯源 UI」——合并到 C8，B3 只做注入。
5. **无验收标准**：所有条目都是一句话方案。§8 修订表已给每项补 DoD（≤3 条）。
6. **交付顺序可优化**：A5 产物卡片（天级、可见度高）应进 Wave 1 首周；B8 拆成 B8a（空态卡+系统打开，已在 09-25 设计文档确认，天级）进 Wave 1、B8b（pdf.js 内联）进 Wave 1.5——「cheap & visible」项不该排在大工程后面。
7. **README 修改的 owner 与口径**：A4 需同步 README.zh-CN.md 与 desktop/README.md 两处（并确认 website/ 无需动——已核验 website 不宣传办公，无需改）。

## 5. B4 移除后的连锁影响与替代建议（B4'）

**影响**：① 主报告 §7 仍把「会议录音→纪要」列为高机会场景、§9-P1#7 仍列为问题——问题陈述与计划现在不一致，需在报告口径上明确「会议场景本季不做、作为已知缺口公示」；② U4（与会者 user story）在矩阵中降为「已知不支持」；③ 与全家桶竞品的对표矩阵中该行放弃，产品叙事需对冲（强调「不碰你的麦克风」的隐私卖点可以把缺口转成立场）。

**替代建议 B4'（可选，零录音基建）**：**转写文件导入**——用户拖入 `.srt`/`.vtt`/`.txt` 转写（市面上任意录音工具/人工速记的产物）→「会议纪要」技能（摘要+行动项+决策提取）→ 行动项一键转 scheduled task。它完全复用 A2/A3/B1 的机器（文件解析+技能+产物卡片），无麦克风/系统音频/whisper 任何新基建，约 2-4 天。用户已决策移除的是**录音流水线**，B4' 不做录音，是否纳入请拍板（§9-Q6）。

## 6. 排期口径修正

原方案「Wave 1 = 2 周 / Wave 2 = 4-6 周」无容量基础（未说明人力假设），且 Wave 1 藏了引擎工程（R6）。修订口径：**Wave 1（1-1.5 周，纯 UI/文案/小后端）→ Wave 1.5（2-3 周，解析与预览）→ Wave 2（4-8 周，与 improvement-plan-2026-09 合并裁决后才能启动）**。所有数字在 Q1 路线 spike 后复核。

## 7. 「不建议做」清单的补充

原三条（Office 加载项/企业全量上下文/credits 计费）维持。补充第四条：**不建议在本轮做「逐页局部重生成」**（原 B2 内含）——它是模板系统成熟后的能力，v1 用「整份重生成但保留已确认大纲」替代，可砍掉一半以上的 UI+状态机工作量。

### 11.2 修正（5 条：结论成立，方案或置信度要调）

- **R1-修正：修复比审查写的更便宜。** 不需要新建 read_document 工具——提取的文本落 `~/.shannon/cache/extracted/<hash>.txt`（带章节标记），复用现有 Read/Grep 工具分页深读，零新工具注册。分节注入+显式截断提示维持不变。

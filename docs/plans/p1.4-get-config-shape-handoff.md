# ADR-0005 P1.4 — `get_config()` return-shape slim (handoff)

> **Status**: 📝 Design only. Not yet implemented. Scope was scoped down
> after an audit revealed 10+ frontend consumers and 30+ fields mixed
> in `DesktopConfig`. Migration is mechanical but invasive — design
> this doc captures the desired shape + migration plan so the next
> sprint can pick it up cleanly.

## Why this exists

P1.2-B removed the singular `provider` / `api_key` / `base_url` /
`model` fields from the top-level `DesktopConfig` (commit `714093e9`).
The engine `ProviderConfigStore` is now the canonical source of truth
for those values. What remains in `DesktopConfig` is a 30-field
mixed bag:

- **Engine client config echoes**: `temperature`, `max_tokens`,
  `performance_strategy` (parity with engine config — used by the
  UI's parameter sliders + status bar).
- **Provider allowlist desktop override**: `enabled_providers`
  (ADR-0005 P4.9 — bridges the engine's `SHANNON_*_PROVIDERS` env
  vars).
- **UI prefs**: `theme`, `working_dir`, `debug_console`.
- **Notification prefs**: `notifications_*` (master + DND window +
  on-completed / on-failed toggles).
- **Skill-loop knobs**: `skill_loop_enabled`, `skill_loop_min_duration_secs`,
  `skill_loop_min_tool_tool_calls`, `skill_detection_enabled`.
- **Gateway supervision**: `gateway` (binary path, extra args, managed
  switch).
- **STT provider config**: `stt` (provider / api_key / base_url / model).
- **Approval mode**: `approval_mode`.
- **OPC strategic focus**: `strategic_focus`.
- **Memory / telemetry / encryption**: `memory_enabled`,
  `telemetry_enabled`, `encryption_enabled`.
- **Plan echo**: `plan`.
- **MCP servers list**: `mcp_servers`.

This single struct is the body of `get_config()`. Every consumer
accesses fields directly (`config?.provider`, `config?.temperature`,
etc.) without grouping.

## Proposed shape

```rust
#[derive(Debug, Clone, Serialize, Deserialize, Default)]
pub struct DesktopConfig {
    /// LlmClientConfig-shaped slice used by the chat runtime + status bar.
    /// Mirrors the fields `build_client_config` reads from
    /// `ProviderConfigStore`. No provider/api_key (engine owns those).
    pub client_config: ClientConfigSlice,

    /// Long-lived user prefs not tied to a specific provider.
    pub user_prefs: UserPrefs,

    /// Notifications / skill-loop / gateway knobs. Distinct section
    /// because they round-trip as a unit in the Settings → Advanced pane.
    pub ui_settings: UiSettings,
}

#[derive(Debug, Clone, Serialize, Deserialize, Default)]
pub struct ClientConfigSlice {
    pub provider: Option<String>,
    pub model: Option<String>,
    pub temperature: Option<f32>,
    pub max_tokens: Option<u32>,
    pub performance_strategy: Option<String>,
    pub version: Option<String>,
    pub strategic_focus: Option<String>,
}

#[derive(Debug, Clone, Serialize, Deserialize, Default)]
pub struct UserPrefs {
    pub working_dir: Option<String>,
    pub theme: Option<String>,
    pub approval_mode: Option<String>,
    pub memory_enabled: Option<bool>,
    pub telemetry_enabled: Option<bool>,
    pub encryption_enabled: Option<bool>,
    pub plan: Option<String>,
    pub enabled_providers: Option<Vec<String>>,
}

#[derive(Debug, Clone, Serialize, Deserialize, Default)]
pub struct UiSettings {
    pub debug_console: bool,
    pub notifications_master_enabled: bool,
    pub notifications_dnd_enabled: bool,
    pub notifications_dnd_start: Option<String>,
    pub notifications_dnd_end: Option<String>,
    pub notifications_on_completed: bool,
    pub notifications_on_failed: bool,
    pub skill_loop_enabled: bool,
    pub skill_loop_min_duration_secs: u64,
    pub skill_loop_min_tool_calls: usize,
    pub skill_detection_enabled: bool,
    pub stt: Option<SttConfig>,
    pub gateway: GatewayDesktopConfig,
    pub mcp_servers: Vec<McpServerConfig>,
}
```

## Migration plan

### Step 1 — Rust struct refactor (no wire change yet)

Add the three new structs as-is. Keep `DesktopConfig` with all 30+
fields as deprecated aliases that delegate to the new sections.

```rust
impl DesktopConfig {
    pub fn client_config(&self) -> ClientConfigSlice { ... }
    pub fn user_prefs(&self) -> UserPrefs { ... }
    pub fn ui_settings(&self) -> UiSettings { ... }
}
```

This step is purely additive — no consumer breaks.

### Step 2 — `get_config()` returns the new shape

Switch the return type from `DesktopConfig` to the new struct.
Acceptance:
- `coreMock.ts` is updated to mock the new shape (3 sections).
- All frontend consumers update to read from the new sections.
- `CatalogContext` / `AppContext` expose `config.client_config.X`
  rather than `config.X`.

This is the heavy step — 10 files, ~40 call sites.

### Step 3 — `configure()` accepts dotted keys

Replace the existing flat-key routing with `client_config.X` /
`user_prefs.X` / `ui_settings.X` dotted paths. Mirrors the
`provider.model` / `provider.tier` convention the engine already uses.

Examples:
- `configure({ key: 'temperature', value: '0.8' })` →
  `configure({ key: 'client_config.temperature', value: '0.8' })`
- `configure({ key: 'working_dir', value: '/Users/x' })` →
  `configure({ key: 'user_prefs.working_dir', value: '/Users/x' })`
- `configure({ key: 'theme', value: 'dark' })` →
  `configure({ key: 'user_prefs.theme', value: 'dark' })`

This step requires migrating every `configure({ key, value })` call
site AND every `getProviderAllowlist` / `gatewayReadConfig` /
`gatewayWriteConfig` consumer that hand-rolls a key string.

### Step 4 — Drop deprecated flat keys

After one release cycle (one sprint), remove the flat-key aliases
from `DesktopConfig`. `configure()` rejects unknown keys.

## Why deferred from this session

- **Frontend blast radius**: 10 files, ~40 call sites. Each
  consumer must be touched to read from the right section.
- **Test coverage is currently 34%** (vitest threshold is 80%).
  Refactoring a surface that is not comprehensively tested is a
  regression risk — a renamed field would silently break every
  caller that hasn't been individually exercised.
- **`configure()` key vocabulary** is also used by the Settings UI
  sliders / pickers (ModelsSettings, AdvancedSettings). Those
  components drive their value updates through `configure({ key,
  value })` with hardcoded strings. Each one is a call site to
  update.
- **The current shape is not actively broken** — `get_config()`
  works, `configure()` works, the UI consumes everything correctly.
  This is a hygiene refactor, not a bug fix.

## Recommended sequencing

1. Land the strict-mode coverage pass first (separate sprint). Without
   it the rename is a regression landmine.
2. Pick this up next once `pnpm test:coverage` is at threshold.
3. Land in three PRs:
   - PR-A: Steps 1 + 2 + frontend migration to the new shape.
   - PR-B: Step 3 (`configure()` dotted keys) + Settings UI
     consumer updates.
   - PR-C: Step 4 (drop flat-key aliases) after one release cycle.

# P1.2 — Remove `DesktopConfig` Singular Fields + Welcome Wizard Rewrite

**Status**: pending (handoff from 2026-07-30 session).
**Branch**: `dev`.
**Estimated effort**: 1.5–2 days.
**Priority**: HIGH — see "Why now" below.

## Why now

P1.1 (`3be764b8` — `refactor(desktop): build_client_config reads from ProviderConfigStore`)
changed `AppState::build_client_config` to read from the engine `ProviderConfigStore`
**on the read path**. But the write path (`configure` and `switch_provider` in
`desktop/src/commands_config.rs`) **still mutates `DesktopConfig` only**. Result:
the runtime client is built from the store, but writes only update the legacy
mirror. The two diverge silently — users can change provider via the Welcome
wizard or Settings panel and have nothing reach the engine runtime.

The same broken path is exercised by the Welcome wizard:
- `desktop/ui/src/pages/Welcome.tsx:270` — `api.configure({ key: 'api_key', value: apiKey })`
- `desktop/ui/src/pages/Welcome.tsx:272` — `api.switchProvider({ provider, model: '' })`

Both bypass the engine store. **Until P1.2 lands, the desktop cannot reliably
switch providers at runtime.**

## Scope

Three concentric layers of work. Sub-task A is the bare minimum to stop the bleed;
Sub-task B is the structural cleanup; Sub-task C is the UX rewrite.

### Sub-task A — Route `configure` through the engine store (1 day)

`desktop/src/commands_config.rs::configure` has 4 match arms that currently
write only to `DesktopConfig` + `state.client_config`:

| `update.key` | Today | Target |
|---|---|---|
| `"model"` | Sets `desktop_cfg.model` + `cfg.model` | `ProviderConfigStore::set_active({ provider_id, model_id })` (preserve active provider_id) |
| `"api_key"` | Sets `desktop_cfg.api_key` + `cfg.api_key` (PLAINTEXT — A1 violation) | `CredentialManager::store_credential(svc, key)` (write to `~/.shannon/credentials/<svc>.json` 0600). Resolve provider_id from active target; reject if no active. |
| `"base_url"` | Sets `desktop_cfg.base_url` + `cfg.base_url` | `ProviderConfigStore::upsert_profile` to update the active profile's `base_url` (preserving all other fields). |
| `"provider"` | Sets `desktop_cfg.provider` (and indirectly the engine path via `build_client_config` reading from store — but no store write!) | `ProviderConfigStore::set_active` for the new provider_id. |

The `"api_key"` arm is the **A1 violation** — it stores plaintext in
`desktop/config.json`. This arm must be removed or routed through
`CredentialManager`. Recommended: route through `CredentialManager` and remove
plaintext persistence entirely.

`state.model` (the legacy in-memory model mutex) becomes redundant — remove
once `model` is routed through the store.

### Sub-task B — Remove `DesktopConfig.provider/api_key/base_url/model` (0.5 day)

The 4 fields are write-through caches for the Welcome flow. With Sub-task A
done, they're no longer the source of truth and can be removed.

Files affected:
- `desktop/src/config.rs` — `pub provider: Option<String>`, `pub api_key: Option<String>`, `pub base_url: Option<String>`, `pub model: Option<String>` — delete fields, all their default handling, and the `mask_providers` mirror.
- `desktop/src/commands.rs` — `AppState` fields `model: Arc<Mutex<String>>`, `provider: Arc<Mutex<String>>` — remove.
- `desktop/src/commands_config.rs` — `switch_provider` (line 487) — rewrite to call `land_profile_in_engine_store` (already exists from Phase 2 task 4) + `ProviderConfigStore::set_active`.
- `desktop/src/commands_config.rs` — `set_active_provider` (line 1143) — already routes through `land_profile_in_engine_store` (per P1.1 fix) — verify.
- `desktop/src/commands_notifications.rs` / `commands_chat.rs` / wherever `state.provider` / `state.model` / `desktop_cfg.provider` etc. are read — update to read from `ProviderConfigStore` or `state.client_config` (which is rebuilt by `build_client_config` after each store write).

Tests: every test that constructs `DesktopConfig { provider: ..., api_key: ..., ... }` needs updating to omit those fields (default empty `..Default::default()`).

### Sub-task C — Welcome wizard rewrite (1 day)

`desktop/ui/src/pages/Welcome.tsx` currently has a `welcome.model` step that
collects an API key + provider label, then calls:
```
await api.configure({ key: 'api_key', value: apiKey })     // line 270
await api.switchProvider({ provider, model: '' }).catch(...) // line 272
```

After Sub-task A, both bypass paths are gone. The wizard must:
- Reuse the `AddProviderModal` from `desktop/ui/src/components/settings/AddProviderModal.tsx` (added in P2.3).
- On submit, call `api.saveProvider` (which routes through `land_profile_in_engine_store`).
- Then call `api.setActiveProvider` to make the just-added provider the active target.
- Drop the bare `<input type="password">` flow (lines 230-260 area — verify by reading the file) — replaced by the modal.

The `welcome.model.title` / `welcome.model.subtitle` / `welcome.model.apiKey.*`
i18n keys (in `desktop/ui/src/i18n/locales/{en,zh-CN}.json` around line 55-67)
can either be deleted or repurposed as a "We recommend Anthropic" hint that
launches the modal with the recommended provider pre-filled (via `editing` prop).

## Acceptance

- `DesktopConfig` no longer has `provider/api_key/base_url/model` fields.
- `AppState` no longer has `model` / `provider` mutexes.
- `configure` rejects unknown keys, and known keys (`working_dir`, `enabled_providers`, `strategic_focus`, etc. — preserve existing handlers) all route through their authoritative store.
- Welcome wizard launches the Add Provider modal instead of taking a raw API key.
- `switch_provider` and `set_active_provider` both update the engine store and emit `CONFIG_UPDATED`.
- `cargo clippy --workspace --lib --bins -- -D warnings` clean.
- `just test` green.
- `pnpm test` (vitest) green.
- `pnpm lint` clean.
